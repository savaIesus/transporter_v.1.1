# ConveyerThree — трёхкамерная линия

Production-версия системы визуальной инспекции и сортировки корпусов для
комплекса с **тремя USB-камерами**. Архитектура, протоколы контроллера,
модель работы с камерами и архивом полностью приведены к уровню
основного (семикамерного) приложения в корне репозитория; от трёхкамерника
сохранена только его инспекционная логика:

- роли камер `LEFT` / `MIDDLE` / `RIGHT` (`camera_mapping.json`);
- модели и правила трёхкамерника (`windows_4.pt`, `shells.pt`,
  `bottom_glass_new_v3.pt`, `welding_new_2.pt`, `iou=0.0`, семантика
  `kind`);
- одна стадия инспекции: все три камеры смотрят в зону `+0`, выброс на `+3`.

## Схема линии

```text
+0  INSPECT     LEFT + MIDDLE + RIGHT: наличие детали и все дефекты
+3  SORT        подготовка маршрута распределителя
+4  DROP        корпус проходит распределитель и покидает учёт
```

Первый шаг после «ПУСК» выполняется без движения ленты — проверяется корпус,
уже стоящий под камерами. Дальше обычный цикл: подготовка маршрута на `+3`,
шаг ленты (`G3 N<seq>` с адресным ACK и подтверждением `STEP` через I2),
пауза затухания вибрации, последовательный захват стоп-кадров, модели,
правила, решение, архив, review.

## Камеры и модели

| Роль    | camera_mapping.json | Модели                                       | Что контролирует                |
| ------- | ------------------- | -------------------------------------------- | ------------------------------- |
| LEFT    | 0                   | `windows_4.pt`, `shells.pt`                  | разновысотность, раковины окон  |
| MIDDLE  | 1                   | `bottom_glass_new_v3.pt`, `welding_new_2.pt` | стекло на дне, брак сварки      |
| RIGHT     | 2                   | `windows_4.pt`, `shells.pt`                  | разновысотность, раковины окон  |

Файлы весов в репозиторий не входят — смотрите `weights/README.md`.

Камеры открываются и читаются как в семикамернике: одно
`cv2.VideoCapture(id)` на роль, успешного `isOpened()` достаточно, один
`cap.read()` в момент времени на всю линию, ошибка захвата — `FAULT` без
автоматического восстановления. На инспекционный блок (`CAPTURE…PUBLISH`)
live-просмотр заморожен целиком и возвращается только на следующем `MOTION`.

## Правила инспекции

- `part_presence` (служебное) — наличие детали по окнам на LEFT/RIGHT;
- `uneven_heights` — разновысотность ячеек окон: вертикальная секущая через
  середину окна, высота в px; брак при `h_max ≥ max`, `h_min ≤ min` или
  разбросе `≥ difference` (пороги раздельно для LEFT и RIGHT);
- `window_sinks` — раковины в окнах (детекции `shells.pt`);
- `bottom_glass` — стекло на дне (CLEANUP-дефект);
- `welding` — брак сварки (CLEANUP-дефект).

Приоритеты итогового решения: `window_sinks` (100) > `uneven_heights` (99) >
`bottom_glass` (80) > `welding` (70) > годно (1).

## Протокол контроллера

Используется текущий диалект прошивки `firmware/convey15.ino` (файл
байт-в-байт совпадает с семикамерником):

- шаг ленты `G3 N<seq>` — принимается только следующий номер, контроллер
  отвечает `ACK G3 STEP=<seq>`; повтор команды при потерянном ACK запрещён,
  завершение подтверждается полем `STEP` статуса `I2`;
- поиск порта требует `STEP=` в ответе контроллера (старые прошивки,
  не подтверждающие физическое завершение шага, отбрасываются);
- чтение ответов — с окнами ожидания первых байтов и паузой тишины
  (`QUIET_PERIOD`): многострочные ответы не обрезаются;
- абсолютные перемещения осей `G27`, парковка `G28`, плавный/аварийный
  стоп `G0`/`G1`;
- обе заслонки распределителя едут одновременно (`move_absolute_async` +
  `_move_parallel`); отдельная пауза падения корпуса не нужна.

## Архив

Архив обязательный, политика не настраивается (как в семикамернике):
`<ROLE>.jpg`, `<ROLE>_raw.jpg`, `<ROLE>_debug.jpg` и `meta.json` в
`GOOD/BAD/CLEANUP/part_NNNN/`, `batch.json` и накопительный `stats.json`;
JPEG с качеством 98, при выходе всегда создаётся ZIP Deflate, проверяется
CRC и удаляется исходная папка партии. `archive_config.json` содержит
только корневую папку.

При завершении программы закрытый (`CLOSED`) `batch.json` отправляется на
ПК аналитика (`json_sender.py`): манифест копируется в локальную очередь
`Protocols\json\<партия>\`, затем уезжает на сетевой диск `Z:\` в
`<партия>\batch.json`; при каждом старте программы очередь догружается,
поэтому партии не теряются, пока ПК аналитика выключен. Отправка идёт
в общем worker-потоке со сжатием архива и ограничена тем же таймаутом;
корень архива берётся из `archive_config.json`.

## Структура приложения

```text
main.py                  тонкая точка входа (run.bat)
application/             composition root и жизненный цикл
  bootstrap.py           сборка приложения, проверка маппинга
  factory.py             создание камер, vision, инспекции, оборудования, цикла
  startup.py             последовательность инициализации и стартовые кадры
  shutdown.py            детерминированное завершение и освобождение ресурсов
  callbacks.py           EXIT (штатный/форсированный) и редактор порогов
  lifecycle.py           связка startup/UI/shutdown
  runtime.py             разделяемое между стадиями состояние
  status.py              начальный снимок статуса линии для HMI
  ui.py                  запуск pywebview и сигналы
  constants.py           тайм-ауты жизненного цикла
core/
  cycle/                 ProductionCycle, разложенный по миксинам
    orchestrator.py      пуск/стоп, главный цикл, авария, OFFSET_INSPECT/+3
    step.py              фазы шага и единственная стадия INSPECT
    diagnostics.py       предстартовые и сервисные проверки
    jog.py               ручной ход
    status.py            телеметрия, анализ кадра, публикация в HMI
  rule_report/           golden-совместимые строки отчёта по правилам
  decision_engine.py     оркестратор правил
  live_preview.py        живой просмотр камер (полное замораживание)
  state_machine.py       состояния линии
  step_stages.py         фазы шага и exclusive-передача камер
domain/                  Part, правила дефектов, геометрия, загрузчик порогов
inspection/              Inspector (одна стадия), run_report, обязательный архив
vision/                  CameraManager (последовательный), VisionCluster, UI
```

## Запуск

Требования: Windows, Python 3.11, зависимости из `requirements.txt`
(для разработки/тестов — дополнительно `requirements-dev.txt`).

```bat
setup.bat
run.bat
```

- `run.bat` — production-режим (HMI в pywebview + реальное железо по COM);
- `run_camera_calibration.bat` — консольная калибровка камер
  (`camera_mapping.json`);
- `camera_check.bat` — консольная диагностика USB-камер без запуска линии;
- `python ui_simulation.py` — прогон HMI без оборудования (симуляция ленты,
  распределителя и камер) для проверки интерфейса.

При закрытии окна HMI консоль скрывается сразу: фоновая очистка (остановка
цикла, камеры, COM-порт, сжатие архива, отправка `batch.json` аналитику)
проходит незаметно. При аварийном выходе консоль возвращается, и `run.bat`
показывает причину ошибки.

### GPU (CUDA)

`setup.bat` при обнаружении драйвера NVIDIA дополнительно ставит CUDA-сборку
PyTorch (индекс — `TORCH_CUDA_INDEX`, по умолчанию `cu128`; переустановка
`--force-reinstall --no-deps torch torchvision`, иначе torchvision остаётся
от CPU-сборки и версии расходятся). Устройство
inference задаётся переменной `VISION_DEVICE`: `auto` (по умолчанию, GPU при
доступном CUDA), `cpu`, `gpu`/`cuda`, `cuda:N` или индекс `0`, `1`, ...
При сбое прогрева на GPU система автоматически переходит на CPU
(`[VISION WARN] ... falling back to cpu`); о выборе устройства говорит строка
`[VISION] Device: ...` в журнале после «Загрузки моделей».

## Конфигурация

- `camera_mapping.json` — привязка ролей LEFT/MIDDLE/RIGHT к индексам камер;
- `thresholds.json` — пороги правил по секциям `LEFT`/`MIDDLE`/`RIGHT` +
  `disabled_rules`;
- `calibration.json` — механика (шаги, скорости, позиции распределителя);
  формат и набор ключей совпадают с семикамерником;
- `archive_config.json` — корневая папка обязательного архива.

> [!CAUTION]
> Программа управляет реальной механикой. Перед запуском должны быть доступны
> независимый аварийный останов, исправные концевики и безопасная зона вокруг
> ленты и распределителя.
